### The Physics of Dictation Latency

When evaluating voice dictation tools, perceived speed is the single most critical factor determining whether speaking feels faster than typing on a mechanical keyboard. An average typist operates at 60–80 words per minute (WPM), while natural human speech flows at 150–220 WPM.

However, if a dictation tool introduces a 600ms latency pause between when you finish speaking and when characters appear on screen, the cognitive flow is broken.

There are two fundamentally different architectural pipelines for voice transcription:

```
Cloud Pipeline:
[Microphone] → [PCM Audio Buffer] → [Opus Encoder] → [TLS Packet] → [Public Internet (30-150ms)] → [Cloud Ingress Queue] → [Server GPU Inference (80-200ms)] → [TLS Stream] → [Desktop App] → [Cursor Injection]
Total Latency: 450ms – 1,200ms (High Jitter)

Local-First Pipeline (HushWrite):
[Microphone] → [Ring Buffer RAM] → [Local GPU whisper.cpp (40-120ms)] → [Win32/macOS SendInput] → [Active Cursor]
Total Latency: 120ms – 180ms (Deterministic)
```

### Why Network Jitter Destroys Cloud Dictation

Cloud dictation providers frequently advertise raw model inference speeds of "sub-100ms on cloud H100 clusters." However, this metric ignores the physical reality of the internet packet journey:

1. **Audio Packetization & Compression:** Converting raw 16kHz PCM audio to Opus chunks takes 20–40ms.
2. **WebSocket & TLS Round-Trips:** Network packets must navigate local Wi-Fi, ISP routing, peering exchanges, and cloud load balancers. On home broadband, this adds 35–90ms; on mobile hotspots or coffee shop Wi-Fi, it routinely spikes past 300ms.
3. **Cloud Concurrency Queues:** When thousands of users dictate simultaneously, requests queue at the server edge, introducing unpredictable latency tails ($p99 > 1,200\text{ms}$).
4. **Local Hardware Acceleration:** In contrast, running `whisper.cpp` locally on an NVIDIA, AMD, or Apple Silicon GPU executes directly in unified memory or dedicated VRAM, completely bypassing the network stack.

### Quantization: The Sweet Spot Between Memory and Word Error Rate (WER)

Running full-precision FP32 or FP16 Whisper models locally requires significant VRAM (up to 3GB for `large-v3`). HushWrite utilizes integer quantization (Q4_0, Q5_1, and Q8_0) to achieve near-lossless accuracy with 60% lower memory bandwidth:

```
Model Comparison (WER vs Memory Footprint):
• Whisper Base (Q5_1):  92 MB VRAM  | 4.8% WER  | 95ms decode
• Whisper Small (Q5_1): 190 MB VRAM | 3.1% WER  | 145ms decode (Default Starter)
• Whisper Large-v3-Turbo (Q5_0): 540 MB VRAM | 1.8% WER | 185ms decode (Pro Tier)
• Full FP16 Large-v3:  3,100 MB VRAM | 1.7% WER | 380ms decode
```

For 98% of professional writing tasks (emails, pull requests, Slack chats, and documentation), `small-q5_1` offers the optimal balance of instantaneous tail response and state-of-the-art vocabulary comprehension.
